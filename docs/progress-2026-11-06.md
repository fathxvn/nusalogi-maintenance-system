Alur Customer Site yang diselesaikan:

1. Detail Customer menyediakan tombol **Tambah Site**, termasuk ketika daftar masih kosong.
2. Form menampilkan nama customer sebagai identitas baca saja, dengan `site_name`, `address`, `pic_name`, dan `pic_phone`.
3. POST membuat site melalui `$customer->sites()->create(...)`. `customer_id` berasal dari model customer pada URL; payload tidak dapat memilih pemilik lain. `id` dan timestamp dari payload juga diabaikan.
4. Berhasil menyimpan mengarahkan kembali ke Detail Customer, menampilkan pesan **Site berhasil ditambahkan.**, jumlah site dan baris lokasi baru.
5. Setiap baris mempunyai aksi **Edit**. Form memuat nilai saat ini dan memakai PATCH untuk menyimpan perubahan.
6. Kedua route edit/update memakai `scopeBindings()`: site di luar relasi customer pada URL menghasilkan 404. Payload `customer_id` juga tidak dapat memindahkan site.
7. Nama site wajib, string UTF-8, maksimal 150 karakter; alamat wajib, string UTF-8, maksimal 65.535 byte; nama PIC opsional maksimal 150 karakter; telepon PIC opsional maksimal 30 karakter. PIC dapat dikosongkan. Batas alamat diperiksa berdasarkan byte, bukan jumlah karakter, sesuai kolom MySQL `TEXT`.
8. Seluruh endpoint berada dalam grup `auth` dan `role:admin` yang sama dengan Customer, dengan middleware akun aktif/disetujui yang sudah ada. Role lain, guest, admin nonaktif, pending, dan rejected diuji.

**Aturan data dan histori:** kode wajib/unik maksimum 50 karakter; kategori wajib maksimum 100; merek/model opsional maksimum 100; nomor seri opsional maksimum 150. Seluruh string divalidasi UTF-8; site wajib ID integer yang ada. Tanggal opsional memakai format `Y-m-d`, cast date dan serialisasi tanggal tanpa waktu; nilai opsional dapat dikosongkan. Unique update mengecualikan ID model pada URL, bukan ID payload. Status, ID, customer_id dan timestamp dari payload diabaikan. Lokasi asset ber-WO tidak dapat dipindahkan, termasuk WO selesai, sementara data perangkat lainnya dapat diperbarui. Kegagalan validasi tidak menyimpan perubahan sebagian.

**Implementasi hapus dan perbaikan:**

- Menambahkan `destroy()` dan named route DELETE dalam grup auth/admin. Asset hilang atau sudah terhapus menghasilkan 404; guest diarahkan ke login, role lain ditolak, akun nonaktif/pending/rejected dikeluarkan sesuai middleware aktif.
- Memeriksa seluruh migration/relasi yang merujuk Asset. Relasi masuk adalah pivot `work_order_assets.asset_id` dengan FK RESTRICT; asset sendiri memiliki FK ke Customer Site. Laporan/foto/invoice berada melalui WO. Tidak ada detach, cascade atau migration baru.
- Penghapusan memakai transaksi, memuat ulang asset dengan `lockForUpdate()`, lalu memeriksa `workOrders()->exists()` tanpa membatasi status. Bila terkait, server mengembalikan error `asset`: “Asset tidak dapat dihapus karena masih terkait Work Order atau histori pekerjaan.”
- FK RESTRICT tetap menjadi pengaman database. Error MySQL 1451/SQLSTATE 23000 diterjemahkan menjadi pesan yang sama setelah rollback; error database lain tetap dilemparkan. Tes menyisipkan relasi pada event deleting untuk membuktikan jalur FK/rollback, bukan menyatakan sudah menguji dua transaksi konkuren nyata.
- Tombol Hapus tersedia pada daftar dan detail, membuka dialog berisi kode, merek/model dan nomor seri. Batal atau membuka dialog tidak mengirim request. Hanya konfirmasi mengirim DELETE. Ref dan state processing mencegah submit berulang serta penutupan selama request. Error server tampil sebagai alert dalam dialog; gagal tidak menutup dialog, selesai dapat dicoba kembali. Berhasil kembali ke daftar dengan “Asset berhasil dihapus.”
- Dialog memakai Title/Description dari Base UI, label trigger per asset, tombol Batal/Hapus, aria-busy, warna destructive dan pembungkusan identitas panjang. Focus trap, Escape dan pemulihan fokus mengikuti primitive yang ada; perilaku browser tetap perlu QA.
- Assertion escaping detail lama menghitung seluruh salinan kode pada HTML. Trigger Hapus menambahkan satu salinan pada aria-label sehingga assertion lama gagal meski escaping benar. Assertion kini menghitung field pada panel detail dan tetap menolak markup berbahaya di seluruh halaman; dialog juga memiliki tes escaping tersendiri.
